Frequently Asked Questions

What is URL encoding?

URL encoding (percent-encoding) replaces unsafe ASCII characters with a % followed by their hex value. It ensures special characters in URLs don't break the URL structure. E.g., a space becomes %20.

What's the difference between encodeURI and encodeURIComponent?

encodeURI encodes a complete URL and preserves URL structural characters like /, ?, &, #. encodeURIComponent encodes a URL component (like a query parameter value) and also encodes these structural characters. Use encodeURIComponent for values in query strings.

When do I need URL encoding?

You need URL encoding when passing user input as URL query parameters, when building API requests with special characters in values, or when creating redirect URLs that contain query strings.

Is my text sent to a server when encoding or decoding?

No, both encoding and decoding happen instantly in your browser using JavaScript's built-in functions. Nothing you enter is transmitted anywhere.

What characters get encoded?

Any character outside the small set considered "safe" in URLs — letters, digits, and a handful of symbols like -, _, ., and ~ — gets converted to its percent-encoded form, including spaces, ampersands, question marks, and non-ASCII characters.

Can I decode an already-encoded URL to read it?

Yes, paste the encoded URL or string into the decode field and it will convert all percent-encoded sequences back into their original readable characters.

How Percent-Encoding Works

Percent-encoding replaces an unsafe character with a percent sign followed by the character's hexadecimal byte value. A space, for example, becomes %20. An ampersand (&) becomes %26. A forward slash becomes %2F. This encoding scheme lets any character, including ones outside the basic ASCII set, be represented using only the limited character set that's guaranteed to be safe inside a URL. When a browser or server receives a percent-encoded URL, it decodes these sequences back into their original characters before processing the request.

encodeURI vs. encodeURIComponent: Which to Use

JavaScript provides two related but different encoding functions, and picking the right one matters. encodeURI is designed for encoding a complete URL — it leaves structural characters like /, ?, &, and # untouched, since those characters have special meaning in the overall URL structure and shouldn't be encoded if you're encoding an entire address. encodeURIComponent, by contrast, is designed for encoding a single component or value — like one query parameter's value — and it does encode those structural characters, since within a single value, a literal & or ? should be treated as data rather than as part of the URL's structure. As a general rule, use encodeURIComponent when encoding a value that will be placed inside a query string, and reserve encodeURI for encoding an entire URL that already has its structure in place.

Common Situations That Require URL Encoding

  • Passing user input as a query parameter. If a search term contains spaces or special characters, it needs to be encoded before being appended to a URL as a parameter value.
  • Building API request URLs. Many APIs require specific values, like API keys or search terms, to be properly encoded within the request URL.
  • Creating redirect URLs. A URL used as a redirect target, especially one that itself contains a query string, often needs to be encoded to avoid the outer URL misinterpreting the nested one.
  • Sharing URLs with special characters. International domain names, file paths with spaces, or URLs containing non-English text frequently need encoding to display and function correctly everywhere.

Decoding: Reading an Encoded URL

Decoding reverses the process, converting percent-encoded sequences back into their original, human-readable characters. This is useful when you've copied a URL from a browser address bar or server log and it's full of %20s and %2Fs that are hard to read at a glance — decoding it instantly reveals the actual text or parameter values being passed, which is especially helpful when debugging why a particular link or API call isn't behaving as expected.

A Common Mistake: Double Encoding

One issue that trips up developers regularly is double encoding — accidentally encoding a string that's already been encoded once, which turns the percent signs from the first encoding pass into their own encoded form (%25) and produces a broken, unreadable result when decoded incorrectly or passed to a system expecting single encoding. This typically happens when a value gets encoded both on the client side and again on the server side, or when a URL is constructed by concatenating an already-encoded parameter into a string that then gets encoded again as a whole. If a decoded URL still contains %25 sequences or other garbled percent signs, double encoding is usually the cause, and the fix is to decode it twice, or better, to trace back through the code and remove the redundant encoding step.
