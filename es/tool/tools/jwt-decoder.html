Preguntas frecuentes

¿Esto verifica la firma JWT?

No, esta herramienta solo decodifica y muestra el encabezado y la carga útil; no verifica la firma, que requiere la clave secreta o pública utilizada para firmar el token.

¿Es seguro pegar un JWT aquí?

La decodificación se realiza completamente en su navegador y el token nunca se envía a un servidor, pero como medida de precaución general, evite pegar tokens con datos de producción altamente confidenciales en cualquier herramienta.

¿Por qué cualquiera puede leer la carga útil de un JWT?

Los JWT se codifican mediante Base64-URL, no se cifran; esto es intencional, ya que los JWT están diseñados para ser legibles pero a prueba de manipulaciones a través de su firma, no confidenciales.

¿Qué significa la declaración "exp" en una carga útil decodificada?

"exp" significa tiempo de expiración, una declaración JWT estándar que almacena una marca de tiempo Unix que indica cuándo el token ya no debe considerarse válido, utilizada por los sistemas receptores para rechazar los tokens caducados.

¿Por qué falla la decodificación con un error?

Esto suele significar que el texto pegado no es un JWT válido; compruebe que tenga exactamente tres partes separadas por puntos y que nada se haya truncado o alterado accidentalmente al copiarlo.

¿Puedo usar esto para comprobar si los tokens de mi propia API están estructurados correctamente?

Sí, este es un caso de uso común durante el desarrollo: decodificar un token emitido por tu propio backend para confirmar visualmente que las declaraciones esperadas están presentes y formateadas correctamente antes del lanzamiento.

Decodificar tokens JWT en línea

Esta herramienta decodifica un JSON Web Token (JWT) y muestra su encabezado y carga útil en formato JSON legible, directamente en tu navegador. Es útil para depurar problemas de autenticación, inspeccionar las declaraciones del token y comprender qué datos contiene realmente un JWT.

Estructura JWT

Un JWT consta de tres partes separadas por puntos: una cabecera, una carga útil y una firma. La cabecera suele especificar el algoritmo de firma y el tipo de token. La carga útil contiene las declaraciones propiamente dichas: datos como el ID de usuario, la fecha de caducidad y cualquier campo personalizado que haya incluido el emisor. La firma es un hash criptográfico que permite al sistema receptor verificar que el token no ha sido manipulado, siempre que disponga de la clave secreta o pública correcta.

¿Por qué los JWT son legibles pero no confidenciales?

Un error común es creer que los JWT están cifrados. No lo están: la cabecera y la carga útil simplemente se codifican en Base64-URL, una codificación de texto reversible, no un cifrado. Cualquier persona que tenga un JWT puede decodificar su cabecera y carga útil al instante, tal como lo demuestra esta herramienta. Esto es intencional: los JWT están diseñados para ser a prueba de manipulaciones (mediante la firma) en lugar de confidenciales. Los datos sensibles que no deberían ser legibles por quien posea el token nunca deben incluirse en la carga útil de un JWT.

Dónde se utilizan comúnmente los JWT

Los JWT aparecen en todas las aplicaciones web y móviles modernas, principalmente como tokens de autenticación emitidos tras un inicio de sesión exitoso, que se incluyen en las solicitudes posteriores para demostrar la identidad del usuario sin necesidad de que vuelva a iniciar sesión en cada solicitud. También se utilizan en flujos de OAuth e inicio de sesión único, tokens de acceso a API para integraciones de terceros y, en algunos casos, para transmitir de forma segura datos estructurados entre servicios que confían en la misma clave de firma. Reconocer la estructura general de un JWT (tres segmentos Base64 separados por puntos) es una habilidad útil para cualquiera que trabaje con API web modernas, ya que encontrarlos en el encabezado de una solicitud o en la respuesta de una API es extremadamente común en los sistemas backend actuales.

Reclamaciones comunes encontradas en una carga útil JWT

Si bien la carga útil de un JWT puede contener cualquier dato personalizado que el emisor decida incluir, existen varios nombres de declaración estándar en la mayoría de las implementaciones. "sub" (sujeto) generalmente identifica al usuario que representa el token. "iat" (emitido en) registra la fecha de creación del token. "exp" (expiración) especifica cuándo debe dejar de aceptarse el token. "iss" (emisor) identifica el sistema que generó el token. "aud" (audiencia) especifica el sistema al que está destinado el token. Reconocer estos nombres de declaración estándar facilita la comprensión de la estructura de un token desconocido a simple vista, ya que siguen una convención consistente en la mayoría de las implementaciones de JWT en lugar de ser específicos de un solo sistema.

¿Por qué esta herramienta no verifica las firmas?

Para verificar la firma de un JWT se requiere la misma clave secreta (para algoritmos HMAC como HS256) o la clave pública correspondiente (para algoritmos RSA/ECDSA como RS256) que se utilizó para firmarlo; información que solo el servidor emisor debería tener. Dado que esta herramienta no tiene acceso a dicha clave secreta, y obtenerla anularía el propósito de mantenerla confidencial, esta herramienta se limita a decodificar y mostrar el contenido del token sin pretender verificar su autenticidad.

Casos de uso comunes para la decodificación de un JWT

  • Depuración de problemas de autenticación : comprobación de si un token contiene el ID de usuario o las declaraciones de rol esperados.
  • Verificación del tiempo de expiración : confirmar que la declaración "exp" de un token coincide con la duración de sesión prevista durante el desarrollo.
  • Comprender los tokens de una API de terceros : inspeccionar qué datos contiene realmente el token de un servicio externo.
  • Aprender cómo funcionan los JWT : ver la estructura de encabezado/carga útil/firma de primera mano en lugar de solo leer sobre ello de forma abstracta.

Privacidad y procesamiento local

Toda la decodificación se realiza directamente en su navegador mediante la decodificación Base64 integrada de JavaScript; su token nunca se envía a un servidor, ni se registra, ni se almacena en ningún lugar.

Nota sobre el manejo de tokens de producción reales

Aunque esta herramienta nunca transmite nada de lo que se pega, sigue siendo una buena práctica general evitar pegar tokens de sistemas de producción en vivo que contengan sesiones de usuarios reales en cualquier herramienta de terceros, incluida esta, simplemente por costumbre. Para el desarrollo y la depuración, generar un token de prueba con declaraciones ficticias o usar un token de un entorno de desarrollo local permite lograr el mismo objetivo de inspección sin involucrar ningún dato vinculado a un usuario real o a un sistema en producción.

¿Por qué los JWT se volvieron tan ampliamente utilizados?

Los JWT se popularizaron principalmente porque son autónomos y sin estado: un servidor puede verificar la validez de un token utilizando solo la firma y la clave secreta, sin necesidad de consultar un registro de sesión en una base de datos para cada solicitud. Esto hace que los JWT sean especialmente adecuados para sistemas distribuidos y arquitecturas de microservicios, donde múltiples servicios independientes necesitan verificar la identidad de un usuario sin consultar un almacén de sesiones centralizado compartido. La desventaja es que las declaraciones de un JWT, una vez emitidas, no se pueden revocar fácilmente antes de su vencimiento sin infraestructura adicional, una consideración que conviene tener en cuenta junto con la comodidad que ofrece esta herramienta para inspeccionar y depurar.
