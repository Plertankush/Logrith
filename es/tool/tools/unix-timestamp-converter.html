Frequently Asked Questions

What is a Unix timestamp?

A Unix timestamp, also called epoch time, is the number of seconds that have passed since 00:00:00 UTC on 1 January 1970, not counting leap seconds. It is a single number that identifies one moment in time, regardless of time zone.

How do I tell whether a timestamp is in seconds or milliseconds?

Count the digits. A current timestamp in seconds has 10 digits, in milliseconds 13, in microseconds 16 and in nanoseconds 19. The converter uses this rule to detect the unit automatically and shows what it chose.

Why does JavaScript give me a 13-digit number?

Date.now() and new Date().getTime() return milliseconds, while many languages and databases use seconds. Divide by 1000 to get seconds, or multiply seconds by 1000 before passing them to new Date().

Does a Unix timestamp depend on time zone?

No. The number is always counted from the UTC epoch. Time zones only matter when you display the moment as a calendar date and clock time, which is why this tool shows UTC and the zone you choose.

What is the Year 2038 problem?

Systems that store the timestamp as a signed 32-bit integer overflow on 19 January 2038 at 03:14:07 UTC. Modern systems use 64-bit values, which last for billions of years, but old embedded devices and file formats may still be affected.

Can a Unix timestamp be negative?

Yes. Negative values are moments before 1 January 1970. For example, -86400 is 31 December 1969 at 00:00:00 UTC.

Is my data sent anywhere?

No. The conversion runs entirely in your browser with built-in date functions, and nothing you type is uploaded.

Unix time is the standard way computers record a moment. Databases, log files, authentication tokens, APIs, file systems and programming languages all use it because a single integer is easy to store, sort and compare, and it does not change with daylight saving or time zones. The difficulty is that people cannot read it. This tool closes that gap without needing a command line or a code snippet.

What the number means

A Unix timestamp counts the seconds that have elapsed since the Unix epoch, 00:00:00 Coordinated Universal Time (UTC) on 1 January 1970. Leap seconds are not counted, so every day is treated as exactly 86,400 seconds. A timestamp of 0 is the epoch itself, 86400 is one day later, and negative numbers refer to moments before 1970.

Seconds, milliseconds, microseconds and nanoseconds

Different systems use different precision. The classic Unix timestamp is in seconds and currently has 10 digits. JavaScript, Java and many web APIs use milliseconds, giving 13 digits. Some databases and tracing tools use microseconds (16 digits), and Go and some logging systems use nanoseconds (19 digits). When you paste a number, the converter counts the digits and picks the matching unit, then tells you which one it chose. If your value is from an unusual source, check that detected unit before trusting the date.

Time zones and daylight saving

The timestamp itself never changes with the time zone. Only the calendar date and clock time shown to a human do. The converter shows the UTC time in ISO 8601 form, which is what most APIs expect, plus the same moment in your local zone or another zone from the list, including New York, London, Berlin, Kolkata, Singapore, Tokyo and Sydney. When you convert a date to a timestamp, you tell the tool which zone you typed it in, and it applies that zone’s offset on that specific date, including daylight saving changes, before producing the number.

Where developers use epoch time

  • Debugging logs, where events are stamped with a number and you need to know when they happened.
  • JWT and session tokens, which carry iat and exp claims as Unix seconds.
  • Databases that store created and updated times as integers.
  • API requests that take a start and end time as timestamps.
  • Cron jobs and scheduled tasks, where you want to check the exact run time.
  • Cache and expiry values, such as Expires or TTL fields.

Common mistakes

  • Mixing seconds and milliseconds. Passing a seconds value to a function that expects milliseconds gives a date in January 1970. Passing milliseconds where seconds are expected gives a date tens of thousands of years away.
  • Reading a UTC time as local time. A timestamp converted to a date is correct only in the zone you state. Always label the zone when sharing a time.
  • Forgetting that months are zero-based in some languages. In JavaScript, new Date(2026, 0, 1) is January, not February.
  • Using 32-bit storage. A signed 32-bit integer can only hold dates up to 19 January 2038, so use a 64-bit type for new systems.

Quick reference in code

In JavaScript, Math.floor(Date.now() / 1000) gives the current timestamp in seconds, and new Date(seconds * 1000).toISOString() turns one back into a date. In Python, int(time.time()) returns the current time in seconds and datetime.fromtimestamp(ts, tz=timezone.utc) converts it. In a Unix shell, date +%s prints the current timestamp and date -d @1735689600 converts one on Linux.
