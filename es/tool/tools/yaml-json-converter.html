Preguntas frecuentes

¿Admite YAML/JSON anidado?

Sí, se admiten objetos anidados y matrices de cualquier profundidad en ambas direcciones de conversión.

¿Qué características de YAML son compatibles?

Se admiten pares clave-valor estándar, asignaciones anidadas, listas, cadenas, números, booleanos y valores nulos. No se admiten funciones avanzadas de YAML como anclas, alias ni archivos multidocumento.

¿Por qué algunos proyectos utilizan YAML en lugar de JSON?

En general, se considera que YAML es más legible para los humanos en lo que respecta a los archivos de configuración, ya que no requiere comillas alrededor de las claves ni llaves, aunque JSON sigue siendo el estándar para el intercambio de datos entre programas.

Convertir entre YAML y JSON

Esta herramienta convierte documentos YAML a JSON, o JSON a YAML, y admite objetos y matrices anidados. Resulta útil para desarrolladores que trabajan con archivos de configuración, manifiestos de Kubernetes, pipelines de CI/CD y API que utilizan cualquiera de estos formatos.

YAML frente a JSON

Tanto YAML como JSON representan las mismas estructuras de datos subyacentes: objetos (pares clave-valor) y matrices (listas ordenadas), pero con sintaxis diferente. JSON utiliza llaves, corchetes y claves entre comillas, lo que facilita su análisis por parte de los programas. En cambio, YAML utiliza sangría y una puntuación mínima, lo que muchos desarrolladores consideran más sencillo de leer y escribir a mano, especialmente para archivos de configuración, aunque a costa de ser más sensible a la precisión de la sangría.

Dónde se usa comúnmente YAML

  • Archivos de configuración : muchas herramientas modernas (Docker Compose, GitHub Actions, Ansible) utilizan YAML para la configuración.
  • Manifiestos de Kubernetes : las definiciones de recursos de Kubernetes se escriben casi exclusivamente en YAML.
  • Las definiciones de los pipelines de CI/CD (compilación e implementación) se escriben frecuentemente en YAML.
  • Generadores de sitios estáticos : en muchos generadores de sitios estáticos, el encabezado utiliza la sintaxis YAML.

¿Por qué convertir entre los dos?

La conversión entre YAML y JSON resulta útil cuando una API espera un formato pero los datos de origen están en otro, al depurar consultando la configuración YAML en formato JSON más explícito o al migrar el formato de configuración de un proyecto. Dado que ambos formatos representan datos subyacentes idénticos, la conversión entre ellos no produce pérdida de información para los tipos de datos estándar.

Privacidad y procesamiento local

Toda la conversión se realiza directamente en tu navegador; tus datos nunca se envían a un servidor.

Cómo el analizador YAML maneja la estructura

Este convertidor lee YAML línea por línea, utilizando el nivel de sangría de cada línea para determinar su posición en la estructura general. Cuando la sangría aumenta, el analizador la interpreta como un objeto o lista anidada; cuando disminuye, cierra el nivel de anidamiento actual y vuelve a uno menos profundo. Los elementos de lista se reconocen por un guion inicial, y cada par clave-valor separado por dos puntos se interpreta como un valor escalar o el inicio de un nuevo bloque anidado, dependiendo de si hay algo después de los dos puntos en la misma línea.

¿Qué tipos de valores se reconocen?

  • Booleanos : las palabras literales true y false se convierten en booleanos JSON.
  • Los valores nulos — null, ~ o un valor vacío se convierten a JSON null.
  • Números : los valores numéricos sin comillas se convierten en números JSON en lugar de cadenas de texto.
  • Las cadenas entre comillas —los valores encerrados entre comillas simples o dobles— se descomponen y se mantienen como cadenas sin formato.
  • Cadenas simples : cualquier cosa que no sea un valor booleano, nulo o numérico reconocido se trata como una cadena.

¿Qué sucede al convertir JSON de nuevo a YAML?

En sentido inverso, la herramienta recorre el objeto JSON analizado de forma recursiva: los objetos anidados se convierten en bloques con sangría, las matrices se convierten en listas con prefijo de guion (y los objetos anidados dentro de una matriz obtienen su propio bloque con sangría), y los valores escalares se escriben como texto plano a menos que parezca que podrían interpretarse erróneamente como un número, un valor booleano o nulo; en cuyo caso se entrecomillan para preservar su tipo original como cadena.

Para desarrolladores que trabajan con Kubernetes y CI/CD

Los manifiestos de Kubernetes, los flujos de trabajo de GitHub Actions y los archivos Docker Compose están escritos en YAML, pero las herramientas de depuración, las API y muchas bibliotecas estándar de lenguajes de programación funcionan de forma más natural con JSON. Convertir temporalmente un manifiesto a JSON facilita la validación de la estructura, la comparación con la respuesta de una API o la introducción en un validador de esquemas JSON, para luego volver a convertirlo a YAML una vez finalizado el proceso.

Limitaciones a tener en cuenta

Este convertidor admite las características YAML más comunes en los archivos de configuración: asignaciones anidadas, listas y tipos escalares estándar. No admite anclas ni alias YAML (referencias &/* para reutilizar bloques), archivos multidocumento separados por --- ni colecciones en línea de estilo flow, como {key: value} escritas en una sola línea. Si su archivo YAML requiere estas características avanzadas, una biblioteca YAML específica las gestionará de forma más fiable.

Errores comunes

  • Mezclar tabulaciones y espacios para la indentación: YAML (y este analizador) se basa en un espaciado consistente, y una tabulación mal colocada puede desplazar un bloque completo al nivel de anidamiento incorrecto.
  • Olvidar la comprobación de la coma final en el modo JSON: un JSON válido nunca tiene una coma final después del último elemento de un objeto o matriz.
  • Suponiendo que los números entre comillas se mantengan como números, un valor YAML como "30" entre comillas se mantiene intencionalmente como una cadena, no se convierte al número 30.

Por qué la indentación importa más en YAML que en JSON

La estructura de JSON se define mediante sus llaves y corchetes, por lo que los espacios en blanco entre tokens son puramente estéticos: se puede minimizar un archivo JSON a una sola línea y aun así se analizará correctamente. YAML no tiene tales delimitadores; la indentación es lo único que le indica al analizador dónde termina un bloque y comienza otro. Por eso, un archivo YAML que se ve casi idéntico a uno que funciona correctamente puede fallar al analizarse si una sola línea tiene una indentación de un espacio en lugar de dos; también es por eso que la conversión a JSON es una útil comprobación de coherencia, ya que las llaves resultantes hacen que el anidamiento real sea visible y sin ambigüedades.

Flujo de trabajo típico para la depuración de archivos de configuración

Un patrón común entre los desarrolladores es pegar una configuración YAML que se comporta de forma inesperada en esta herramienta, convertirla a JSON y comparar visualmente el anidamiento con lo previsto. Dado que las llaves de JSON hacen explícito cada nivel de anidamiento, suele ser más rápido detectar una clave mal colocada o un array que se ha convertido accidentalmente en un objeto que examinar la indentación YAML sin procesar.
