Ciberseguridad y código abierto

Explicación de las licencias de código abierto: MIT, Apache, GPL y cómo elegir la más adecuada.

Por Plert Ankush · Publicado 12 de noviembre de 2026 · Actualizado 12 de noviembre de 2026 · 3 minutos de lectura

Casi todos los proyectos modernos dependen de código abierto, y cada fragmento de ese código viene con una licencia. La licencia determina qué se puede hacer con él: usarlo comercialmente, modificarlo, mantener los cambios en privado o incluirlo en un producto. Un error en este aspecto puede acarrear problemas legales o la obligación de reescribir el código, mientras que hacerlo correctamente requiere menos esfuerzo del que la mayoría piensa.

Esta guía explica las principales familias de licencias y las más populares dentro de cada una, y ofrece una forma sencilla de elegir la más adecuada para tu proyecto. Se trata de información general, no de asesoramiento legal.

Conclusiones clave

  • La ausencia de licencia no significa que su uso sea gratuito. Por defecto, el código sin licencia tiene todos los derechos reservados.
  • Las licencias permisivas (MIT, BSD, Apache 2.0) permiten una amplia reutilización con condiciones poco restrictivas.
  • Las licencias Copyleft (GPL, AGPL) exigen que las obras derivadas se compartan bajo términos similares.
  • Para tu propio proyecto, MIT o Apache 2.0 son opciones comunes y sencillas.

¿Qué hace una licencia de código abierto?

La ley de derechos de autor otorga a los creadores derechos exclusivos sobre su obra. Una licencia de código abierto concede a otras personas permisos específicos por adelantado, generalmente para usar, copiar, modificar y distribuir el código, a cambio de cumplir ciertas condiciones. Estas condiciones constituyen la principal diferencia entre las licencias.

La Open Source Initiative mantiene una lista de licencias que cumplen con la definición de código abierto. Las licencias que restringen el uso comercial o ciertos campos no son de código abierto, incluso si el código es de acceso público.

Dos familias: permisiva y copyleft

Las licencias permisivas permiten hacer casi cualquier cosa, incluso usar el código en productos comerciales de código cerrado, siempre que se mantenga el aviso de derechos de autor y el texto de la licencia. Las licencias copyleft añaden un requisito: si se distribuye una obra basada en el código, la versión propia debe publicarse bajo la misma licencia o una compatible. El objetivo es mantener el código y sus derivados como código abierto.

Las licencias que necesitarás con mayor frecuencia

Por qué es importante la concesión de patentes

Los derechos de autor y las patentes son derechos independientes. Alguien podría contribuir con código y posteriormente reclamar derechos de patente sobre él. Apache 2.0 y la GPL v3 incluyen licencias de patentes explícitas, lo que brinda mayor seguridad a los usuarios. Las licencias MIT y BSD no se pronuncian sobre las patentes, lo cual es aceptable para muchos proyectos pequeños, pero es una de las razones por las que las organizaciones más grandes suelen preferir Apache 2.0.

Utilizar de forma segura el software de código abierto de otras personas

  1. Sepa de qué depende. Enumere las dependencias directas e indirectas y sus licencias. La mayoría de los gestores de paquetes pueden generar este informe.
  2. Conserva los avisos. Casi todas las licencias exigen que conserves el aviso de derechos de autor y el texto de la licencia. Muchos sitios los recopilan en una página de créditos o de licencia.
  3. Verifica la política de copyleft antes de publicar. Si distribuyes software que incluye código GPL u ofreces código AGPL como servicio de red, asegúrate de comprender primero las obligaciones de uso compartido.
  4. Considera el código sin licencia como prohibido. Si un repositorio no tiene un archivo de licencia, no tienes permiso para reutilizarlo.
  5. Mantén actualizadas las dependencias. Los proyectos mantenidos solucionan problemas de seguridad. Los abandonados se convierten en un riesgo.

Elegir una licencia para su proyecto

  • Si buscas la máxima adopción con el mínimo esfuerzo: MIT.
  • Usted desea lo mismo, además de protección de patentes y condiciones de contribución claras: Apache 2.0.
  • Si desea que las mejoras se mantengan abiertas: GPL v3 para aplicaciones o LGPL para bibliotecas.
  • Usted administra un servicio alojado y no desea que otros alojen una bifurcación cerrada: AGPL v3.

Añade un archivo LICENSE en la raíz de tu repositorio y menciona la licencia en tu archivo README. Recursos como choosealicense.com explican la decisión con más detalle.

Licencias para cosas que no son código

Las licencias Creative Commons son adecuadas para artículos, imágenes y otras obras creativas, no para software. Si publicas tanto código como contenido, utiliza una licencia de software para el código y una licencia Creative Commons para el contenido. En el Logrith, los créditos de las bibliotecas utilizadas en las herramientas del navegador se recogen en la página de licencias .

Preguntas frecuentes

¿Puedo utilizar código con licencia MIT en un producto comercial?

Sí. La licencia MIT permite el uso comercial, la modificación y la distribución siempre que se incluya el aviso de derechos de autor y el texto de la licencia.

¿El uso de software GPL me obliga a publicar mi propio código como código abierto?

Depende de cómo lo uses. Si distribuyes una obra combinada que deriva de código GPL, la GPL exige que la publiques bajo la misma licencia. Generalmente, ejecutar internamente software GPL sin modificar no implica esta obligación. Consulta con un abogado especializado para tu caso particular.

¿Qué ocurre si un proyecto no tiene licencia?

Por defecto, el autor conserva todos los derechos, por lo que no está permitido copiar, modificar ni distribuir el contenido sin su permiso.

¿El software de código abierto es gratuito?

Normalmente se puede obtener sin pagar, pero el concepto de "código abierto" se refiere a las libertades que otorga la licencia, no al precio.
