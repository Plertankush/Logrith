JSON vs YAML vs XML vs CSV: Which Data Format Should You Use?

By Logrith Team · Published Nov 12, 2026 · Updated Nov 12, 2026 · 4 min read

Every application eventually has to store data in a file or send it to another system. The four formats you will meet most often are JSON, YAML, XML and CSV. They overlap enough that people argue about them, yet each has a clear sweet spot.

This guide compares them side by side, points out the mistakes that cause real bugs and finishes with a simple way to choose.

Key takeaways

  • Use JSON for APIs and data exchange between programs.
  • Use YAML for human-edited configuration, and watch its whitespace and type-guessing traps.
  • Use XML when you need documents with mixed content, namespaces or strict schemas.
  • Use CSV for flat tables you want to open in a spreadsheet. It has no types and no nesting.

JSON: the default for data exchange

JSON (JavaScript Object Notation) represents data as objects (key-value pairs), arrays, strings, numbers, booleans and null. It is compact, easy for programs to parse in virtually every language and strict enough that parsing errors are easy to detect.

Strengths: universal support, small and predictable syntax, clear data types.

Weaknesses: no comments, no trailing commas, every key and string needs double quotes, and large numbers can lose precision in some languages. Hand-editing is tedious for big files.

When a JSON file will not parse, the cause is usually a missing comma, a trailing comma or single quotes. Paste it into a JSON formatter to see exactly where it breaks, or try JSON Repair for common mistakes.

YAML: readable configuration

YAML aims to be easy for humans to read and write. It uses indentation instead of braces, allows comments and supports the same kinds of structures as JSON. It is widely used for configuration, such as CI pipelines and container definitions.

Strengths: very readable, supports comments, concise for nested configuration.

Weaknesses:

  • Whitespace matters. A wrong indent changes the meaning, or breaks the file. Use spaces, never tabs.
  • Type guessing. Unquoted values can be interpreted as other types. In YAML 1.1, words like no or off may be read as booleans, which has caused the well-known "Norway problem" where the country code NO becomes false. Quote ambiguous strings.
  • Complexity. Features like anchors and multi-document files are powerful but easy to misuse.

Need to move between the two? A YAML to JSON converter helps you check that a config means what you think it means.

XML: structure for documents

XML wraps data in named tags and attributes. It is verbose, but that verbosity supports features the others lack: namespaces to avoid name clashes, schemas that validate structure strictly, and mixed content where text and markup interleave, as in documents.

Strengths: strong validation, mature tooling, ideal for document-like data, and still common in feeds, office file formats and enterprise or government integrations.

Weaknesses: verbose, heavier to parse and harder to read than JSON for plain data. A XML formatter makes large files bearable to inspect.

CSV: simple tables

CSV stores one record per line with values separated by commas. Every spreadsheet program can open it, which makes it the standard export format for tabular data.

Strengths: tiny, universal, perfect for rows and columns.

Weaknesses: no data types (everything is text until a program guesses), no nesting, and several subtle traps:

  • Values containing commas or line breaks must be wrapped in quotes, and quotes inside must be doubled.
  • Different tools use different delimiters (comma, semicolon, tab) and encodings.
  • Spreadsheets may silently reformat values, such as dropping leading zeros from IDs or turning gene names into dates.

If a file is messy, the CSV Cleaner can tidy common problems before you import it.

A simple way to choose

  1. Will programs exchange it? Use JSON.
  2. Will a person edit it often, with comments helpful? Use YAML, carefully quoted, or JSON if you can live without comments.
  3. Is it a document or must it satisfy a formal schema or an existing standard? Use XML.
  4. Is it a flat table meant for a spreadsheet or analysis tool? Use CSV.

If you are unsure, start with JSON. It is supported everywhere, and converting later is usually straightforward.

Common mistakes to avoid

  • Putting comments in JSON. They are not allowed, so use a "_comment" field or switch to YAML.
  • Using YAML for data that machines write and read. Prefer JSON for generated files.
  • Opening and re-saving CSV in a spreadsheet, which can change values without warning.
  • Mixing tabs and spaces in YAML.
  • Choosing XML out of habit when the data is a simple object.

Frequently asked questions

Is YAML a superset of JSON?

Valid JSON is generally valid YAML 1.2, so most JSON files can be read by a YAML parser. The reverse is not true, because YAML has many features JSON lacks.

Why is JSON more common than XML for web APIs?

It is lighter, simpler to read, and maps directly to the objects and arrays used in most programming languages.

Can CSV hold nested data?

Not directly. You can flatten nested data into columns or store a JSON string in a cell, but at that point JSON is usually a better fit.

Which format is fastest?

It depends on the parser and the data. For most applications readability, tooling and correctness matter more than raw parsing speed.
