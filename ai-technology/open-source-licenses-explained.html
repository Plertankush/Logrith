Open Source Licenses Explained: MIT, Apache, GPL and How to Choose

By Logrith Team · Published Nov 12, 2026 · Updated Nov 12, 2026 · 3 min read

Almost every modern project depends on open source code, and every piece of that code comes with a licence. The licence decides what you may do with it: use it commercially, modify it, keep your own changes private or ship it inside a product. Getting this wrong can mean legal trouble or a forced rewrite, and getting it right takes less effort than most people expect.

This guide explains the main licence families and the popular licences within them, and offers a simple way to choose one for your own project. It is general information, not legal advice.

Key takeaways

  • No licence does not mean free to use. By default, code without a licence is all rights reserved.
  • Permissive licences (MIT, BSD, Apache 2.0) allow broad reuse with light conditions.
  • Copyleft licences (GPL, AGPL) require derivative work to be shared under similar terms.
  • For your own project, MIT or Apache 2.0 are common, low-friction choices.

What an open source licence does

Copyright law gives creators exclusive rights over their work. An open source licence grants other people specific permissions in advance, usually to use, copy, modify and distribute the code, in return for following certain conditions. Those conditions are the whole difference between licences.

The Open Source Initiative maintains a list of licences that meet the open source definition. Licences that restrict commercial use or certain fields are not open source, even if the code is publicly visible.

Two families: permissive and copyleft

Permissive licences let you do almost anything, including using the code in closed-source commercial products, provided you keep the copyright notice and licence text. Copyleft licences add a requirement: if you distribute a work based on the code, you must release your version under the same or a compatible licence. The goal is to keep the code and its descendants open.

The licences you will meet most

LicenceTypeKey points
MITPermissiveVery short. Do almost anything, keep the copyright and licence notice. No explicit patent grant.
BSD (2 and 3-clause)PermissiveSimilar to MIT. The 3-clause version adds a rule against using the authors' names to endorse your product.
Apache 2.0PermissiveIncludes an explicit patent grant and requires noting changes. Common in larger projects.
MPL 2.0Weak copyleftCopyleft applies per file. Changes to MPL files must be shared, but you can combine them with other code.
LGPLWeak copyleftDesigned for libraries. You can link to it from other software under conditions, but changes to the library itself must be shared.
GPL (v2, v3)Strong copyleftDistributed derivative works must be released under the GPL, with source available.
AGPL v3Strong copyleftLike GPL, and extends the requirement to software offered over a network, such as a hosted service.

Why the patent grant matters

Copyright and patents are separate rights. Someone could contribute code and later claim patent rights over it. Apache 2.0 and GPL v3 include explicit patent licences, which gives users more certainty. MIT and BSD are silent on patents, which is fine for many small projects but is one reason larger organisations often prefer Apache 2.0.

Using other people's open source safely

  1. Know what you depend on. List direct and indirect dependencies and their licences. Most package managers can produce this report.
  2. Keep the notices. Almost every licence requires you to keep the copyright notice and licence text. Many sites collect them on a credits or licence page.
  3. Check copyleft before you ship. If you distribute software that includes GPL code, or offer AGPL code as a network service, understand the sharing obligations first.
  4. Treat unlicensed code as off limits. If a repository has no licence file, you do not have permission to reuse it.
  5. Keep dependencies updated. Maintained projects fix security issues. Abandoned ones become a liability.

Choosing a licence for your project

  • You want maximum adoption with minimal fuss: MIT.
  • You want the same, plus patent protection and clear contribution terms: Apache 2.0.
  • You want improvements to stay open: GPL v3 for applications, or LGPL for libraries.
  • You run a hosted service and do not want others to host a closed fork: AGPL v3.

Add a LICENSE file at the root of your repository and mention the licence in your README. Resources such as choosealicense.com walk through the decision in more detail.

Licences for things that are not code

Creative Commons licences suit articles, images and other creative works, not software. If you publish both code and content, use a software licence for the code and a Creative Commons licence for the content. Frequently asked questions

Can I use MIT-licensed code in a commercial product?

Yes. The MIT licence allows commercial use, modification and distribution as long as you include the copyright notice and licence text.

Does using GPL software force me to open-source my own code?

It depends on how you use it. If you distribute a combined work that is a derivative of GPL code, the GPL requires you to release it under the GPL. Running unmodified GPL software internally generally does not trigger that. Check with a qualified lawyer for your specific situation.

What happens if a project has no licence?

By default the author keeps all rights, so you are not allowed to copy, modify or distribute it without permission.

Is open source free of charge?

Usually you can obtain it without paying, but "open source" is about the freedoms the licence grants, not the price.
