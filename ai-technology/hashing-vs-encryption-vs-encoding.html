Hashing vs Encryption vs Encoding: The Difference Explained

By Plert Ankush · Published Nov 12, 2026 · Updated Nov 12, 2026 · 3 min read

Developers and non-developers alike mix up hashing, encryption and encoding. They all turn data into something that looks different, but they solve different problems, and using the wrong one is a classic security mistake. Storing passwords with Base64, for example, protects nothing.

This guide gives each concept a clear definition, a comparison table and practical rules for when to use which.

Key takeaways

  • Encoding changes the format of data so systems can handle it. Anyone can reverse it, and it provides no secrecy.
  • Hashing produces a fixed-size fingerprint and cannot be reversed. It is used for integrity checks and, with the right algorithms, for passwords.
  • Encryption hides data and can be reversed only with the right key.
  • Never store passwords with plain encoding, encryption you can decrypt, or fast general-purpose hashes.

Encoding: changing the format

Encoding converts data from one representation to another so it can travel safely through a system that expects a certain format. Base64 turns binary data into plain text characters so it can sit inside JSON or an email. URL encoding replaces unsafe characters in a web address with percent codes.

There is no secret. If you can see Base64 text, you can decode it instantly. Try it yourself with the Base64 tool or the URL encoder. Treat encoding as packaging, never as protection.

Hashing: a one-way fingerprint

A hash function takes any input and produces a fixed-length output, called a hash or digest. The same input always gives the same output, a tiny change in the input produces a completely different output, and you cannot work backwards from the hash to the original data.

Common uses include:

  • Integrity checks. Publish the SHA-256 hash of a download so users can verify the file was not altered.
  • Deduplication. Identical files produce identical hashes.
  • Digital signatures and data structures. Hashes sit inside many security systems.

Not all hash functions are equally safe. MD5 and SHA-1 have known collision weaknesses and should not be used for security purposes, whereas the SHA-2 family, such as SHA-256, remains widely used. You can generate and compare digests with the Hash Generator.

Hashing passwords is a special case

Websites should never store your password itself. They store a hash and compare the hash of whatever you type at login. But a plain, fast hash such as SHA-256 is the wrong tool, because attackers can test billions of guesses per second against stolen hashes.

Password storage should use a deliberately slow algorithm built for the job, such as Argon2, bcrypt or scrypt, with a unique random salt for each password. The salt ensures that two users with the same password get different hashes and defeats precomputed lookup tables. Use a well-reviewed library instead of writing this yourself.

Encryption: secrecy with a key

Encryption scrambles data so that only someone with the correct key can read it. There are two families:

  • Symmetric encryption (for example AES) uses the same key to encrypt and decrypt. It is fast and used for files, disks and most data in transit once a connection is set up.
  • Asymmetric encryption (for example RSA or elliptic-curve systems) uses a public key to encrypt and a private key to decrypt. It solves the problem of sharing keys, and underlies HTTPS certificates and signatures.

The strength of encryption depends on keeping the key secret and on using a modern, well-reviewed algorithm. Inventing your own scheme is almost always a mistake.

A related tool: HMAC and signed tokens

Sometimes you need to prove that data came from someone who knows a secret and was not changed. An HMAC combines a hash function with a secret key to produce that proof. It is how many APIs sign webhooks, and how JSON Web Tokens can be signed. You can inspect the readable parts of a token with the JWT Decoder, remembering that a token's contents are encoded, not encrypted, unless it is specifically an encrypted token.

Practical rules

  1. Need data to travel in a different format? Encode.
  2. Need to verify that data has not changed, or to store passwords? Hash, using SHA-256 for integrity and a password-hashing algorithm for passwords.
  3. Need to keep data secret but readable later? Encrypt, with a modern algorithm and carefully protected keys.
  4. Do not use encoding as security, and do not use fast hashes for passwords.

Frequently asked questions

Is Base64 encryption?

No. Base64 is encoding. Anyone can decode it without a key, so it offers no confidentiality.

Can a hash be reversed?

Not mathematically, but weak or common inputs can be found by guessing and checking, which is why passwords need slow hashes and salts.

Why is MD5 considered broken?

Researchers can produce two different inputs with the same MD5 hash, called a collision, so it cannot be trusted where tampering is a concern.

What is the difference between a hash and a checksum?

A checksum detects accidental errors and is often simple. A cryptographic hash is designed to resist deliberate tampering as well.
