JSON for Developers: A Part-by-Part Guide

By Logrith Team · Published Nov 12, 2026 · Updated Nov 12, 2026 · 6 min read

JSON is the format behind most web APIs, configuration files and data exports, and it is also what AI models are increasingly asked to produce. You can learn the essentials in an afternoon, yet the same few mistakes cause most of the bugs.

This guide is split into five short parts. Read them in order, or jump to the part you need. Each part links to a free browser tool so you can try the idea on your own data as you read.

Key takeaways

  • JSON has only six value types and strict syntax: double quotes, no comments and no trailing commas.
  • Most parse errors come from the same handful of mistakes, so learn to spot them.
  • Always parse in a try/catch (or equivalent) and never trust the shape of data you did not create.
  • Flat records convert cleanly to CSV; nested data needs flattening or should stay as JSON.
  • When an AI model produces JSON, validate it against a schema instead of assuming it is correct.

Part 1: What JSON is and what it can hold

JSON stands for JavaScript Object Notation. It is a plain-text format for structured data, created from the way JavaScript writes objects but now used by almost every programming language. A JSON document is built from just six kinds of value:

  • Object: unordered key-value pairs in curly braces, such as {"name": "Asha"}.
  • Array: an ordered list in square brackets, such as [1, 2, 3].
  • String: text in double quotes.
  • Number: integer or decimal, with no leading plus sign and no quotes.
  • Boolean: true or false, in lowercase.
  • Null: null, meaning an intentionally empty value.

Objects and arrays can contain other objects and arrays to any depth, which is what lets JSON describe real-world data such as a customer with several orders, each with several items.

What JSON cannot hold matters just as much. There is no date type, so dates are written as strings, usually in ISO 8601 form such as "2026-11-15T10:30:00Z". There is no comment syntax, no undefined, no function and no special value for infinity or not-a-number. If you need any of these, you have to agree on a convention with whoever reads your data.

Part 2: Syntax rules and the errors that break JSON

JSON is stricter than JavaScript. A file that looks right to a human often fails a parser. These are the mistakes behind most "Unexpected token" errors:

MistakeExampleFix
Trailing comma{"a": 1,}Remove the last comma
Single quotes{'a': 1}Use double quotes for keys and strings
Unquoted key{a: 1}Write "a"
Comment// noteDelete it, or store it in a "_comment" field
Missing comma{"a": 1 "b": 2}Add a comma between pairs
Unescaped quote or newline in a string"say "hi""Escape as \" and \n
Wrong literalTrue, None, NaNUse true, null, and avoid NaN

To find the exact spot, paste your text into the JSON Formatter, which validates it and shows the position of the first error. If the data came from a log, a chat message or an AI model and has several of these problems at once, the JSON Repair tool can fix the common ones automatically.

Two more details trip people up. Duplicate keys are technically allowed by the syntax but behave differently between parsers, so avoid them. And numbers have no size limit in the format, but most languages read them as 64-bit floating point, so integers larger than 9,007,199,254,740,991 can lose precision in JavaScript. Send very large IDs as strings.

Part 3: Reading and writing JSON in code

Every mainstream language has a built-in or standard JSON library. The two operations you need are parsing (text to data) and serializing (data to text).

JavaScript uses JSON.parse(text) and JSON.stringify(value, null, 2), where the last two arguments produce readable output with two-space indentation. Python uses json.loads(text) and json.dumps(value, indent=2), plus json.load and json.dump for files.

Good habits that prevent most production bugs:

  1. Wrap parsing in error handling. Invalid input raises an exception, and a single bad response should not crash your program.
  2. Do not assume the shape. Check that the keys you need exist and have the type you expect before using them. Optional chaining in JavaScript and dict.get() in Python help.
  3. Never use eval to parse JSON. It can execute code. Use the real parser.
  4. Handle dates on purpose. Parse ISO strings into date objects after loading, and convert back when saving. A Unix timestamp converter is useful when an API gives you epoch numbers instead.
  5. Pretty-print for people, minify for machines. Indentation is for reading; removing whitespace makes payloads smaller.

When you work with APIs, also check the Content-Type: application/json header and the HTTP status code before parsing. An error page that comes back as HTML will otherwise show up as a confusing JSON parse error. The HTTP status code lookup explains what each code means.

Part 4: Converting JSON to CSV, YAML and back

JSON often has to move into other formats. The right approach depends on the target.

JSON to CSV. CSV is a flat table, so an array of similar objects maps neatly: each object becomes a row and each key becomes a column. Nested objects can be flattened into dot-notation columns such as address.city, and arrays are best kept as JSON text inside one cell. The JSON to CSV converter does both directions and handles quoting of commas and line breaks. Check the result in a spreadsheet, and remember that spreadsheets can silently reformat values such as long numbers and IDs with leading zeros.

JSON to YAML. YAML expresses the same structures with indentation and allows comments, which makes it popular for configuration. Because most JSON is valid YAML, conversion is usually lossless, but converting back can change types if YAML guesses wrongly, for example reading no as a boolean. Use the YAML and JSON converter to confirm that a config still means what you intended.

Part 5: JSON and AI models

Many applications now ask a language model to return JSON so that other code can use the answer: a list of extracted fields, a classification or a set of tags. This works well, but only if you treat the output as untrusted input.

Models can produce JSON that is almost right: wrapped in extra text or a markdown code fence, with a trailing comma, a missing field or a value of the wrong type. Newer APIs offer a structured output mode that constrains the model to a schema you provide, which reduces these failures a lot. Even so, build a safety net:

  1. Ask for JSON only. State the exact keys and types you expect, and include a short example.
  2. Strip wrappers. Remove code fences and any text before the first brace and after the last one before parsing.
  3. Parse in a try/catch, and on failure retry once with the error message, or fall back safely.
  4. Validate against a schema. Check required keys, types and allowed values with a validator such as JSON Schema, rather than trusting the model.
  5. Mind the length. Long outputs can be cut off mid-object when they hit the model’s output limit, which leaves invalid JSON. Keep outputs small or request them in pieces. The AI context calculator helps you estimate how much text fits.

If a response is only slightly broken, the JSON Repair tool shows what a fix looks like. In production, though, prefer prevention (schemas and validation) over repair, because silently repaired data can hide real problems. To understand why models make these formatting slips at all, read how large language models work.

Quick checklist

  • Double quotes everywhere, no trailing commas, no comments.
  • Large IDs sent as strings.
  • Dates in ISO 8601 or as explicit timestamps.
  • Parsing wrapped in error handling, with shape checks after.
  • CSV exports checked for lost leading zeros and wrong delimiters.
  • AI-generated JSON validated against a schema before use.

Frequently asked questions

Is JSON the same as a JavaScript object?

No. JSON is a text format with stricter rules: keys and strings must use double quotes, and comments, functions and undefined are not allowed. A JavaScript object is an in-memory value that you convert to and from JSON text.

Why does JSON not allow comments?

The format was kept deliberately minimal so it parses the same way everywhere. If you need comments, use YAML, a format such as JSON5 where both sides support it, or a reserved "_comment" key.

How do I store a date in JSON?

As a string in ISO 8601 form, for example "2026-11-15T10:30:00Z", or as a Unix timestamp number. Pick one convention, document it and parse it explicitly after loading.

What is the difference between JSON and JSON Lines?

JSON Lines (NDJSON) stores one complete JSON object per line. It is easy to stream and append to, which makes it common for logs and large datasets, but a whole file is not a single valid JSON document.

Can I trust JSON written by an AI model?

Treat it like any untrusted input. Use a structured output feature if your provider offers one, then parse safely and validate the result against a schema before your code relies on it.
