Frequently Asked Questions

What is a cron expression?

A string of five fields (minute, hour, day of month, month, day of week) used to schedule recurring tasks on Unix-like systems.

What does an asterisk mean?

An asterisk (*) means "every" value for that field — for example, an asterisk in the hour field means the job runs every hour.

How do I run a job every 15 minutes?

Use */15 in the minute field, with all other fields set to *. This means "every 15th minute."

The Five Cron Fields

  • Minute (0-59) — which minute of the hour the job runs.
  • Hour (0-23) — which hour of the day, in 24-hour format.
  • Day of Month (1-31) — which day of the month.
  • Month (1-12) — which month of the year.
  • Day of Week (0-6, Sunday=0) — which day of the week.

Common Cron Syntax Patterns

  • * — matches every value (every minute, every hour, etc.)
  • */N — matches every Nth value (e.g., */15 in minutes means every 15 minutes)
  • N-M — a range of values (e.g., 9-17 in hours means 9 AM to 5 PM)
  • N,M — a list of specific values (e.g., 1,15 in day-of-month means the 1st and 15th)

Why Cron Scheduling Matters

Cron is the standard way to schedule recurring automated tasks on servers — backups, report generation, cache clearing, email digests, and countless other maintenance jobs run on a cron schedule. Getting the expression right is important since a misconfigured cron job can run too often (wasting resources) or not often enough (missing its intended purpose), and the terse five-field syntax is easy to misread without careful attention.

Day of Week Numbering

Cron's day-of-week field runs from 0 to 6, with 0 representing Sunday (some implementations also accept 7 as Sunday). This differs from how people naturally count days starting with Monday, which is a common source of off-by-one scheduling mistakes — for example, setting 1 expecting Sunday when it actually means Monday.

Combining Day-of-Month and Day-of-Week

When both the day-of-month and day-of-week fields are set to specific values rather than *, most cron implementations treat them as an OR condition — the job runs if either condition is true, not only when both match simultaneously. This is a frequently misunderstood part of cron syntax and worth double-checking with the generated explanation before relying on it for a production schedule.

Common Scheduling Use Cases

  • Nightly backups — running a database or file backup once a day during low-traffic hours, such as 0 2 * * * for 2 AM daily.
  • Periodic cache clearing — using an interval like */30 * * * * to clear a cache every 30 minutes.
  • Weekly reports — sending a summary email every Monday morning with an expression like 0 9 * * 1.
  • Monthly billing jobs — triggering invoice generation on the first day of each month with 0 0 1 * *.

Cron vs. Manual Scheduling

Before cron-style schedulers, recurring tasks had to be triggered manually or through custom scripts with their own timing logic. Cron standardized this into a compact, portable syntax that works the same way across Linux servers, container orchestrators, and many SaaS scheduling features, which is why the same five-field format keeps showing up well beyond traditional Unix systems.

Common Mistakes with Cron Expressions

  • Confusing minute and hour order — cron lists minute before hour, which is the reverse of how people usually say a time aloud ("9:30" vs the cron order of minute-then-hour).
  • Forgetting that day-of-month and day-of-week are OR'd together — leaving one as a specific value while meaning "any" can cause a job to run on unexpected days.
  • Using the wrong day-of-week numbering — remember 0 (or 7) is Sunday, not Monday.
