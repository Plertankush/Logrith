SQL Formatter and Beautifier

This tool reformats SQL queries — turning a dense, single-line query into a clean, readable structure with each major clause on its own line and consistent capitalization for keywords.

Why Format SQL Queries?

SQL queries copied from logs, generated by ORMs, or written quickly during debugging are often compressed onto a single line, making them hard to read at a glance. Proper formatting — placing each major clause (SELECT, FROM, WHERE, JOIN, GROUP BY, ORDER BY) on its own line with consistent indentation — makes the query's structure and logic immediately clear, which speeds up debugging, code review, and understanding queries written by others.

What This Tool Does

The formatter identifies common SQL keywords within your query and places each one at the start of a new line, capitalizing it for consistency, while leaving the rest of your query (table names, column names, values, conditions) untouched. This produces a query that's dramatically easier to scan and understand without altering its actual logic or behavior in any way.

Common Uses

  • Debugging — quickly understanding a complex query pulled from application logs.
  • Code review — making SQL in pull requests easier for reviewers to read.
  • Documentation — presenting queries clearly in technical documentation or tutorials.
  • Learning SQL — seeing query structure broken down clause by clause.

Privacy and Local Processing

All formatting happens directly in your browser — your SQL queries are never sent to a server.

How the Keyword Detection Works

The formatter first collapses your query down to a single line by stripping extra whitespace, then walks through a list of recognized clause keywords — starting with multi-word phrases like SELECT DISTINCT, LEFT OUTER JOIN, and INSERT INTO before shorter ones like SELECT, FROM, and SET. Checking longer phrases first prevents a keyword like "JOIN" from being matched and broken apart in the middle of "LEFT JOIN" or "INNER JOIN". Each match is placed at the start of a new line and rewritten in uppercase, so a query written entirely in lowercase comes out with standard, conventional capitalization.

Handling WHERE Clauses with AND / OR

Beyond the main clause keywords, the formatter also looks for AND and OR inside your conditions and indents them two spaces under the WHERE (or HAVING) clause they belong to. This keeps a multi-condition filter — for example status = 'active' AND age > 18 AND country = 'US' — readable as a stacked list of conditions rather than a long unbroken line, which makes it much faster to spot a missing or misplaced condition.

For Developers Working with ORM-Generated Queries

Queries generated by ORMs (Django, SQLAlchemy, Sequelize, Hibernate, Eloquent, and similar) are typically logged as a single compressed line with no formatting at all, since the ORM has no reason to pretty-print its output. Pasting that raw logged query into this tool is often the fastest way to actually read what the ORM sent to the database — especially useful when you're trying to confirm whether a generated query includes the JOINs, WHERE conditions, or LIMIT clause you expected.

For Students Learning SQL

Seeing a query broken into its component clauses — SELECT, FROM, WHERE, GROUP BY, ORDER BY — each on its own line makes the overall structure of a SELECT statement much easier to internalize than reading it as one continuous sentence. Students can paste example queries from textbooks or online tutorials into the tool to see how each clause relates to the others before writing their own queries from scratch.

Manual Formatting vs. Using This Tool

Formatting a short query by hand — adding line breaks and capitalizing keywords — takes only a minute, but queries with several JOINs, nested conditions, or subqueries get tedious and error-prone to reformat manually, especially under time pressure while debugging a production issue. Running the query through this tool takes the same amount of effort regardless of query length and never introduces a typo into a keyword or accidentally changes a value while reformatting.

Limitations to Keep in Mind

The formatter works on recognized keywords and doesn't parse your SQL into a full syntax tree, so it won't reformat the contents of subqueries with extra indentation relative to their parent query, and it doesn't validate that your SQL is syntactically correct — it simply looks for the keywords regardless of whether the surrounding query would actually run. Highly vendor-specific syntax (such as T-SQL's TOP, or PostgreSQL's DISTINCT ON) outside the recognized keyword list is left exactly as typed.

Using It Alongside Code Review

When you're reviewing a pull request that touches raw SQL — a migration script, a reporting query, or a hand-written statement inside application code — pasting it through the formatter before reading it closely can surface issues that are easy to miss in a cramped one-liner, such as a WHERE clause that's missing a condition on one branch of an OR, or a JOIN that's silently a CROSS JOIN because the ON condition was dropped. Reformatting first and then reading top to bottom, clause by clause, is a quick habit that catches more than skimming the original compressed query.

Working with Multiple Statements

If your input contains more than one SQL statement separated by semicolons, the formatter processes the whole pasted block as one piece of text, splitting on whitespace and keywords rather than on statement boundaries. For the clearest output, it generally works best to format one statement at a time, especially when the statements use very different clause structures (for example, one SELECT and one UPDATE in the same paste).
